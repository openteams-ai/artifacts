Linking several GitHub repos to one Plane project

Today each Plane project syncs with a single GitHub repo. This page reviews the approach Plane suggested (run your own sync service), lists what it leaves out, and estimates the work under different scopes.

The approach is soundYour service owns the repo↔project mapping and routing. Plane only receives create and update calls.
The outline is thinIt covers how to connect the pieces. It skips routing, loop prevention, missed webhooks, and identity mapping.
~2.5 wks one-way, ~5–7 wks two-wayOne engineer. Use the estimator below to change the scope.
Check this first · ~½ day

The native integration may already do this. Plane's GitHub docs describe issue sync as a per-project setting ("Project Issue Sync") but never say whether a project can link more than one repo. Try adding a second repo to a sandbox project before building anything. It needs the Pro plan or higher. Self-hosted Plane also needs your own GitHub App.

Operations

Where it runs

The service needs a public HTTPS endpoint for both webhooks, a small database, a queue, and a scheduled job. Pick a hosting option to compare.

Keeping it running

Plan on one named owner and 1–2 days a month. Most of that goes to API changes, new repo mappings, and the occasional drift fix.

Watch

  • Plane webhook turned off. Plane disables it after 5 failed deliveries. Check its status from the reconciler and page someone.
  • Queue depth and dead letters. A growing backlog means an API is rate-limiting or down.
  • Drift found per reconciler run. Should sit near zero. A rise means webhooks are being missed.
  • 429s and 5xx from either API.
  • Signature failures. Usually a rotated secret that wasn't updated in the service.

Routine

  • Rotate secrets every quarter: GitHub App private key, both webhook secrets, Plane app credentials.
  • Dependency updates through Renovate or Dependabot.
  • Follow Plane's API changelog. The API is still changing. Pin the version you call and test against staging before upgrades.
  • Back up Postgres. The link tables are the only record of which issue matches which work item.
  • Review mappings when teams rename, archive or split repos.

When it breaks

  • Pause one mapping. Set its direction to paused. This stops a loop or bad routing without taking down the rest.
  • Replay a time window. Run the reconciler with --since after an outage.
  • Remove duplicates by grouping Plane items on external_id.
  • Rebuild lost links. Plane items carry the GitHub node ID in external_id. Also write the Plane ID into a hidden marker in each GitHub issue, so links can be rebuilt from both sides.

Adding a repo to a project

  1. Give the GitHub App access to the repo in the org's app settings.
  2. Add a repo_project_map row through a PR to the config file or the admin CLI. Set the direction and state map.
  3. Run the backfill for that repo in dry-run mode, check the output, then run it for real.
  4. Create a test issue and confirm it shows up in Plane, and that edits flow back if the mapping is two-way.
