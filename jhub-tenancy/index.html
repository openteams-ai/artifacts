Nebari multi-tenancy · JupyterHub

Notebooks for many tenants: a hub per tenant, or one shared hub?

Recommendation: run two tiers. A shared demo tier (one hub and shared apps on sample data) lets anyone try the platform, holding no tenant credentials and no rights in any tenant. Real work runs in a JupyterHub per tenant, inside the tenant's namespace. Avoid one shared hub that maps users into tenants: it must be able to start pods as every tenant, so one bug or breach reaches all of them.

The two options

Combining data from two tenants needs a deliberate grant in either model

Neither option lets one notebook use two tenants' data by default. In B, each notebook still runs in one tenant namespace with that tenant's identity; the user picks which. To combine data, grant it on purpose: the data owner shares a dataset from tenant A to tenant B read-only, or the collaboration gets a joint tenant of its own.

Recommended shape

Anyone can try the platform in the shared demo tier, which holds only sample data and has no rights in any tenant. To do real work, a user is added to a tenant's group. Notebooks move over through a Git repo; nothing is copied from the demo hub, and tenant data never flows back to the demo tier.

When the shared mapping hub wins

  • Users belong to several tenants. One URL and a profile picker, instead of a separate hub and login for every tenant a user is in.
  • Many small tenants, such as one per project or per person, where N hubs stop being a handful.
  • Tenants are budgets, not boundaries: one organisation splitting quota, with no per-tenant cloud identity.

If you build it anyway: deny by default, match full group paths exactly, and give the hub a Role per tenant namespace rather than a ClusterRole. Avoid letting a shared component impersonate users: unrestricted user impersonation can reach cluster-admin.
