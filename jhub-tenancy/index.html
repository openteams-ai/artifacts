Nebari multi-tenancy · JupyterHub

Notebooks for many tenants: four JupyterHub shapes compared

Four ways to give multi-tenant Nebari users notebooks: A, a JupyterHub per tenant; B, a shared hub that maps users into tenant namespaces through impersonation; B′ (B-prime), a shared hub with a per-tenant profile; and D, a tenant operator that creates A's setup from one resource per tenant. Each is rated on weight, security, work left and time horizon, then compared on tenant self-administration, users in several tenants and gateway auth.

Combining data from two tenants needs a deliberate grant in every option

No option lets one notebook use two tenants' data by default. In B and B′, each notebook still runs with one tenant's identity; the user picks which. To combine data, grant it on purpose: the data owner shares a dataset from tenant A to tenant B read-only, or the collaboration gets a joint tenant of its own.

Questions to settle for B′

  • Should the tenant profile mount only the tenant's own shared directory, and a home claim named per profile, so a member of another shared-storage group can't carry tenant data into that group's directory or into a home used outside the tenant?
  • How are notebooks kept from crowding the tenant's own workloads on its pool?
