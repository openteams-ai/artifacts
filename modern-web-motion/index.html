Part one · Why motion

Motion is feedback, not decoration

orientation

Where did that come from?

A panel that slides in from the right tells you where it lives and which way it goes back.

continuity

Is this the same thing?

A card that grows into a detail page keeps the user's mental model intact. A hard cut makes them rebuild it.

feedback

Did that work?

A button that presses, a row that settles into its new spot. Confirmation without a toast.

hierarchy

What should I look at?

The one thing that moves is the one thing people look at. Use that budget carefully.

The test: if you removed the motion, would the user lose information? If not, it's decoration, and decoration has a very short welcome.

Set the frame for the whole talk. The advanced techniques coming up are only worth it in service of one of these four jobs. Ask the room for the last animation that annoyed them; it almost always fails the test on this slide.

Part one · Why motion

Six kinds of motion, and the tool that fits each

Most UI motion is one of these. Name the kind first; the technique follows.

transitions · @starting-style

State changes

Enter and exit: tooltips, menus, dialogs, toasts. Two states, interruptible, reversible.

FLIP · View Transitions

Layout changes

Reorder, filter, resize, insert. The thing that moved is the same thing; motion keeps that true for the eye.

View Transitions

Navigation

Route changes, tab switches, list to detail, shared-element morphs. Where did I go, and how do I get back.

transform · springs

Feedback

Press, toggle, success, error. Under 200ms, on the thing you touched. Confirmation without a message.

scroll timelines

Scroll-linked

Reveals, parallax, progress, sticky scenes. Driven by position, not time, so it can never fall behind.

@keyframes · sparingly

Continuous

Loading pulses, spinners, attention loops. The only kind with no end state, so it needs a reason to stop.

The split that matters: the first four are motion between two states and should be transitions, so the browser handles interruption and reversal. The last two are motion over time, and need a reason to start and to stop.

One minute. Point at the tags: every technique in part two is on this slide, and part two takes them roughly top to bottom. The callout carries the transition-versus-animation distinction, which is worth saying once: if you can express it as "from state A to state B", make it a transition. Punchlist, in the demos, exercises the first four kinds with one switch.

Part two · The modern toolkit

The platform caught up

Five additions since 2023 cover most of what we used to need a library for. No build step, no bundle.

2023

linear() easing

Any curve as a list of points. Springs and bounces in pure CSS.

2023 → 2025

View Transitions

Snapshot the old DOM, swap, animate between. Page and element morphs.

2023 → 2026

Scroll-driven animations

Progress bound to scroll position, off the main thread.

2024

@starting-style

Transition from display:none. Enter and exit without JavaScript.

2024 · Chromium

interpolate-size

Animate to height: auto. Still Chromium only.

Years are when the first stable browser shipped each feature; the full support table is in part three. Each one maps to a kind of motion from the previous slide. The point is the trend: the platform has absorbed the common cases. The next five slides take one each, with a working example you can poke at.

Part two · View Transitions

You've been watching one on every slide change

The browser captures the old state

document.startViewTransition(cb)

Every element with a view-transition-name gets its own snapshot; everything else is part of root.

Your callback changes the DOM

cb() → swap slides, swap routes, re-render

Any DOM change at all. The page is frozen under the old snapshot while this runs.

Old and new snapshots animate

::view-transition-old(root) / ::view-transition-new(root)

Pseudo-elements you style with ordinary CSS. The default is a crossfade; this deck freezes the old frame and clips the new one.

Part two · @starting-style

Enter and exit from display: none, in CSS alone

/* closed */
.toast { display: none; opacity: 0; translate: 0 10px;
  transition: opacity .22s, translate .22s,
              display .22s allow-discrete; }

/* open */
.toast.open { display: grid; opacity: 1; translate: 0 0; }

/* the frame before "open" applies */
@starting-style { .toast.open { opacity: 0; translate: 0 10px; } }

Two halves: @starting-style gives the entry a "from" state, and transition-behavior: allow-discrete keeps display on until the exit finishes. Base UI's data-starting-style is this pattern with the attribute flipped for you.

Part two · linear() easing

A spring is just a list of points

Run a damped-spring integrator once, sample the curve, and hand it to CSS as linear(…). No runtime physics, no library, and it works on any transition.

03 · cubic-bezier vs. baked spring

stiffness 260 · damping 24
cubic-bezier(.2,0,0,1) · 500ms
linear(…) · spring
Run once with the defaults: the spring arrives with a small settle, the bezier just decelerates. Drop damping to 8 and run again for a visible overshoot; raise stiffness for a snappier arrival. The status line shows the natural duration the spring needs, which you pass alongside the easing. Show code: this is the integrator from Motion Lab's springs.ts, about 40 lines. Presets (soft, snappy, bouncy) can be installed as CSS custom properties once at app start.

Part two · Scroll-driven animations

Bind progress to scroll, not to time

/* the container names a timeline */
.scroller { scroll-timeline: --feed block; }

/* a progress bar reads it */
.bar i { animation: grow linear both;
         animation-timeline: --feed; }

/* each item animates as it enters the viewport */
.item { animation: reveal linear both;
        animation-timeline: view();
        animation-range: entry 0% entry 70%; }

Replaces: scroll listeners, IntersectionObserver reveal hooks, and the jank that comes with them. Runs off the main thread in Chromium.

Part two · Web Animations API

FLIP: let layout happen, then animate the difference

// First: measure
const first = new Map([...items].map(el => [el, el.getBoundingClientRect()]));
// Last: change the DOM (reorder, filter, resize)
reorder();
// Invert + Play: animate from the old box to the new one
for (const el of items) {
  const a = first.get(el), b = el.getBoundingClientRect();
  el.animate([{ translate: `${a.left-b.left}px ${a.top-b.top}px` }, { translate: "0 0" }],
             { duration: 350, easing: "cubic-bezier(.2,0,0,1)" });
}

Why WAAPI: element.animate() is the same compositor path as CSS, but it takes values you computed a millisecond ago. FLIP is the technique every "layout animation" feature in every library is built on.

Part three · Browser compatibility

Progressive enhancement is one if and one @supports

// JS: the swap always runs; the transition is optional
function navigate(update) {
  const reduce = matchMedia("(prefers-reduced-motion: reduce)").matches;
  if (!document.startViewTransition || reduce) { update(); return; }
  document.startViewTransition(update);
}
/* CSS: the enhancement lives inside the guard */
.item { opacity: 1; }
@supports (animation-timeline: scroll()) {
  .item { animation: reveal linear both;
          animation-timeline: view(); }
}
@media (prefers-reduced-motion: reduce) {
  .item { animation: none; }
}

The pattern: write the final state first, with no motion. Add the motion inside a guard. Content is never hidden waiting for an animation that may not run.

This is the slide to slow down on. The failure mode of modern motion isn't "it looks worse in Firefox", it's "the content never appears" because someone set opacity: 0 in the base rule and the reveal animation didn't run. Final state first, enhancement inside the guard.

Part four · Libraries

Use the platform until it costs you code

The platform is enough when…

  • The motion is between two states (enter, exit, open, close, route change)
  • You're animating opacity and transform
  • Reversal and interruption should just work
  • You want zero bundle cost and no version churn

A library earns its place when…

  • Sequences depend on runtime state (choreography across many elements)
  • Gestures: drag with velocity, throw, snap
  • Layout animations across component boundaries you don't control
  • Designer-authored animation (Rive, Lottie) that must match a file exactly

Honest cost: Motion Lab has zero animation libraries, and the price was hand-rolling a spring, a FLIP hook and a particle emitter. For most product UI you won't need any of those.

The point is not "libraries bad". It's that the default flipped: in 2019 you reached for a library first; now the library is the exception you justify. Mention that every library on the next slide now uses WAAPI under the hood where it can, which is why they're smaller and smoother than they used to be.

Part four · Libraries

Four worth knowing, and what each is for

motion.dev · React, JS, Vue

Motion

Formerly Framer Motion; import from motion/react. Hybrid engine: WAAPI where possible, JS where needed. Declarative animate props, layout animations, gestures, AnimatePresence for exits. The default for React apps that need more than CSS.

gsap.com · framework-agnostic

GSAP

Timelines and sequencing. Free for all uses since 3.13, including the formerly paid plugins (SplitText, MorphSVG, DrawSVG and the rest), after Webflow's 2024 acquisition. Best for choreographed marketing and storytelling pages.

animejs.com · small

anime.js

Lightweight timeline library with a tidy API, now at v4. A good fit when you want GSAP-style sequencing without GSAP's size.

rive.app · lottiefiles.com

Rive and Lottie

Designer-authored vector animation played at runtime. Rive adds state machines and interactivity; Lottie is After Effects export. For icons, illustrations and brand moments, not for layout.

Keep this to a minute. If someone asks "which one for us", the answer is on the Nebari slides: CSS and Base UI first, Motion through the render prop when needed. GSAP's free licensing is worth a mention because many people still think it costs money.

Part five · In Nebari

Nebari ships motion tokens; use them, don't invent durations

The @nebari/theme registry item installs these next to the color and radius tokens.

TokenValueUse
--duration-fast100msMicro-interactions: icon swap, badge count
--duration-base200msStandard enter and exit: tooltip, dropdown
--duration-slow350msPage-level overlays: dialog, sheet, drawer
--duration-loading1600msSkeleton pulse
--ease-standardcubic-bezier(.4,0,.2,1)Most transitions
--ease-emphasizedcubic-bezier(.2,0,0,1)Overlays sliding into view

Five ready-made utilities: animate-fade-in, animate-fade-out, animate-slide-up-fade (6px), animate-slide-down-fade, animate-skeleton-pulse. Always behind motion-safe:; the keyframes live inside @theme inline.

Three durations plus a loading pulse, two easings. That's the whole vocabulary, and it's deliberately small: if a motion needs 600ms in product UI, it's probably too much. Note the ceiling: 350ms is for a full dialog. The 200ms base is where most things live, which is the "everyday UI" in the title.

Part five · In Nebari

Four hard rules, and the two gotchas that break them silently

rule 1

Gate on motion-safe:

Every animation class is prefixed: motion-safe:animate-fade-in. WCAG 2.1 SC 2.3.3.

rule 2

Tokens, never literals

var(--duration-base) in CSS, duration-(--duration-base) in classes. Never 0.2s.

rule 3

Animate opacity and transform only

Height, width, padding and top force layout. Use FLIP or View Transitions when position must change.

rule 4

CSS and Base UI first

Reach for a JS library only when the CSS primitives can't express it. Never edit ui/* to add motion; it's overwritten on upgrade.

Gotcha 1, parentheses: Tailwind v4 reads duration-(--duration-base). The v3 bracket form duration-[--duration-base] is invalid, so transition-duration resets to 0s and nothing moves.

Gotcha 2, cn(): tailwind-merge dedupes transition-* against the component's own classes. Re-enumerate every property you need: transition-[color,background-color,transform], not bare transition.

Both gotchas fail silently, which is why they're on the slide. The bracket one has bitten more than one PR. If people remember one thing from this part: motion lives at the call site in globals.css, a CSS module or a wrapper, with tokens, behind motion-safe.

Part five · In Nebari

Base UI already flips the attributes; you write the CSS

Overlay enter and exit, no JavaScript

/* globals.css: Base UI popups set these during transitions */
[data-starting-style] { opacity: 0; transform: translateY(4px); }

[data-starting-style],
[data-ending-style] {
  transition-property: opacity, transform;
  transition-duration: var(--duration-base);
  transition-timing-function: var(--ease-emphasized);
}

applies to Dialog, Popover, Select, Tooltip, Menu: anything built on Base UI's popup primitives.

The escape hatch: Motion through render

import { motion } from "motion/react";
import { Button } from "@/components/ui/button";

<Button render={<motion.button animate={{ scale: [1, .96, 1] }} />}>
  Save
</Button>

Keeps the component's classes and data-* attributes intact. Install Motion only when a screen needs it; it's not a registry dependency.

Left side is the @starting-style pattern from part two, wearing Base UI's attribute names. Right side is the one sanctioned way to bring a library in: through the render prop, so the design-system component stays the source of truth. Use it for staggered lists, state-dependent exits, or spring physics you don't want to bake yourself.

Part six · Where it doesn't belong

Motion that fails the test on slide three

Anything a user waits for

A 400ms entrance on a list the user opens fifty times a day is 20 seconds of their day. Speed up or cut.

Layout properties

Animating height or top re-lays out every frame. If it must move, move a transform or let View Transitions snapshot it.

Autoplaying, looping, ambient

Background motion competes with content for attention and drains batteries. Decorative loops belong on a marketing page, if anywhere.

Hiding content behind it

If the animation doesn't run, the content must still be there. Reduced motion is a hard override, never a soft suggestion.

And the five film wipes? They fail the test for product UI. They're in this deck because a deck is theater, and in Motion Lab because it's a lab. Know which one you're building.

Say the last line with a straight face; it's the honest counterweight for the whole talk. Everything in part two is a tool, and the wipes show that the same API does both tasteful route transitions and film wipes. The craft is in choosing.

Wrap-up

Three things to take away

  1. Motion is feedback. If removing it loses no information, remove it.
  2. The platform covers the everyday cases. Guard each feature and ship the final state first.
  3. In Nebari: tokens, motion-safe:, opacity and transform, at the call site. Libraries come in through render, when they earn it.
