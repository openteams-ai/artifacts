Part one

What Nebari design actually is

A shadcn component registry styled with the Nebari brand. Components are distributed as source, copied into your repo by the shadcn CLI. There is no npm package to import.

Each component is a thin, typed wrapper over Base UI, styled with Tailwind v4 utilities that resolve to one set of semantic tokens.

The entry point is npx shadcn add @nebari/<name>.

Your appcall sites, overrides block
Nebari componentscopied source, upstream-managed
Base UI + cva + lucideprimitives, variants, icons
Tailwind v4 + theme tokens@theme inline mappings
shadcn CLIresolves and copies
Emphasise "source, not a package". People assume there is a version to bump in package.json. There isn't. The CLI copies files into your repo, and that is what the rest of the talk hangs on.

Part one

Why a registry and not a package

An npm component package

  • One version for everyone; a bump lands every change at once
  • Styling is behind a prop API you cannot reach past
  • Extending means wrapping, forking, or waiting on a release
  • Types and Tailwind classes ship precompiled

A shadcn registry

  • You own the files; the diff on upgrade is readable
  • Styling is Tailwind classes on tokens you already have
  • Extending is className and the render prop at the call site
  • Per-item install, with dependencies resolved by the CLI

The trade. Ownership of the files comes with a rule: treat them as upstream-managed. Edit one and the next install overwrites your change.

Do not let this turn into package-bashing. Packages are right for libraries with a stable API. The point is that a design system wants its consumers to see and extend the styling, and a registry makes that the default.

Part two

Four steps to a themed app

Add the registry to components.json beside your existing style, tailwind and alias config. The only prerequisite is a shadcn-initialized project.

{
  "registries": {
    "@nebari": "https://nebari-dev.github.io/nebari-design/r/{name}.json"
  }
}

The theme is a registry:theme item that writes one :root, one .dark and one @theme inline block. Components pull it in transitively, but install it explicitly once.

npx shadcn add @nebari/theme
npx shadcn add @nebari/button @nebari/dialog
npx shadcn add @nebari/use-theme-preference

The tokens name Geist and IBM Plex Mono, but the registry ships no webfonts. Skip this and you get system stacks, which is fine for a prototype and wrong for a product.

npm i @fontsource-variable/geist @fontsource/ibm-plex-mono
import '@fontsource-variable/geist';
import '@fontsource/ibm-plex-mono/400.css';
import '@fontsource/ibm-plex-mono/500.css';

One ThemeProvider owns the .dark class on <html>. Paste the output of themeBootstrapScript() at the top of <head> so a dark-preference user never sees a light frame. This deck does the same with its own storage key.

import { ThemeProvider } from '@/hooks/theme-provider';

<ThemeProvider><App /></ThemeProvider>
Step through all four but only dwell on step two. The theme-install-overwrites behaviour is the thing that bites people later, so plant it here and return to it on the overrides slide.

Part three

One semantic palette, both themes

Switch the theme in the bar. The hex values below are the registry's; they change with it.

--canvas
--header
--card / --popover
--muted
input fill, zebra row, slider track

Four layers, in stacking order. Canvas, then app chrome, then raised surfaces, then a recess used only inside a card or chrome. In light mode a card is separated from the canvas by its border, not its fill. In dark mode recesses lift instead of digging.

--background is deprecated. Its light value equals the header layer, which made headers invisible. New page shells use bg-canvas.

Muted text on a muted surface uses text-muted-foreground-strong. The regular muted foreground fails contrast on the recessed fill.

Toggle dark while the room watches the nested boxes. Point out that the muted layer gets lighter in dark mode, not darker. That is the sentence people misremember.

Part three

Brand, feedback pairs, edges

--primarymagenta-600 light, 500 dark
--primary-hoverpressed and hover fill
--secondaryneutral ramp, no brand hue
infosoft bg + strong fg
successsoft bg + strong fg
warningsoft bg + strong fg
destructivesoft bg + strong fg

Feedback is a pair. A soft background and a strong foreground, mirrored from Figma's background and foreground roles. Alert, Badge and Toast use both halves; nothing uses one alone.

Edges are four tokens. --border for most strokes, --border-strong for the Badge outline, --input for form fields, --ring for focus. Never a hex.

Thirty seconds. The one thing to say out loud: there is a single brand hue. Secondary and accent map to the neutral ramp on purpose, so magenta stays rare and means something.

Part three

Keep your overrides out of the Nebari block

A theme install overwrites every value it owns in the first matching :root, .dark and @theme inline block. That is how token updates reach apps.

So app-owned tokens go in a second block after it. The cascade lets the later declaration win, and the CLI never touches it.

Installing a component only appends tokens that are missing. Only a theme install overwrites.

/* App overrides: below the Nebari theme blocks. */
:root {
  --header-action-hover: #d9d9dc;
  --notification-badge: #d00000;
  --sign-out-foreground: #d2161c;
}
.dark {
  --header-action-hover: #4a4a50;
  --notification-badge: #e00000;
  --sign-out-foreground: #ff6b6b;
}
@theme inline {
  --color-header-action-hover: var(--header-action-hover);
  --color-notification-badge: var(--notification-badge);
  --color-sign-out-foreground: var(--sign-out-foreground);
}
This is the slide that saves someone an afternoon. Edit a Nebari value in place and the next theme install clobbers it silently. Say "second block, after" twice.

Part four

Extend at the call site, never in ui/

Pass classes; cn() lets yours win

<Button variant="outline" size="sm" className="w-full">
  Cancel
</Button>

Swap the element with render

Nebari's equivalent of Radix's asChild. Classes and data-* attributes merge onto the element you pass.

<Button render={<a href="/docs" />}>Docs</Button>

Read the installed source for the API

Exact variant and size names live in each component's cva block and props type. That file, not any doc, is authoritative. npx shadcn view @nebari/button shows it before installing.

Edit components/ui/button.tsx

The next install regenerates the file. It also forks your app away from every other consumer of the same component, which is what a design system exists to prevent.

Restyle with raw hex or dark: variants

Tokens flip with the .dark class on their own. A hard-coded colour is a second theme system that drifts from the first.

// no  <Card className="bg-[#f6e9ff] dark:bg-[#442655]" />
// yes <Card className="bg-muted" />

Install an avatar

There is none in the registry. Each app owns a small one on Base UI's primitive, kept outside components/ui/ so an install cannot overwrite it.

Show Do first, then flip to Don't. The render prop is the thing to say slowly: it is how you get a link that looks like a button without wrapping or forking.

Part four

Tokens for time, not magic numbers

Four durations, two easings, five animate-* utilities. These run on the real values.

fade-in
200ms standard
slide-up-fade
200ms emphasized
1600ms loopReplay
100ms scaleReplay

Hard rules. Gate everything on motion-safe:. Reference tokens with parentheses in Tailwind v4, duration-(--duration-base); the v3 bracket form silently resets to zero. Animate opacity and transform only.

The cn() gotcha. A bare transition class overwrites the component's own transition-property, and its colour transition disappears. Re-enumerate every property you need.

Click replay on the first two so the room sees how short 200 milliseconds is. Then the parentheses rule: it is the single most common motion bug in a Tailwind v4 migration.

Part five

What it asks of you

Being honest here buys credibility for everything else.

A React, Tailwind v4, shadcn stack

The registry is source that assumes all three. A non-React app, or one on Tailwind v3, gets the tokens and the Figma library, not the components.

Discipline over tooling

Nothing stops you editing a file in ui/. The rule is a convention, enforced by review and by the next install undoing your work.

Base UI, not Radix

render instead of asChild, data-starting-style instead of keyframes. Small differences that trip people who know shadcn's defaults.

Some assembly required

Fonts are not shipped. There is no avatar. Three header tokens are app-defined. Each is a five-minute job, and each is a way to drift if skipped.

A licence to read

The design repo is CC BY-NC-ND 4.0. Check that against how your project ships before you adopt it commercially.

Cross-browser is still on you

The registry tests components, not your app. oklch colours and @theme inline want current browsers.

Pick the two closest to what this room builds and dwell there. The licence point is the one people will not have thought about, so do not skip it.
