For engineers adopting the system

How Nebari design reaches your app

Nebari design is a shadcn component registry, not an npm package. Components are copied into your repo as source, styled with one set of semantic tokens, and composed with Base UI. This page shows the pipeline from the registry to your call site, and the handful of rules that keep an app on the system after the first install.

nebari-dev/nebari-design Storybook registry.json globals.css (the tokens)

The pipeline

From Figma variables to your call site

Every hop is public. The one that matters most is the last one: once the CLI has copied a component into your repo, the file is yours to run but not yours to edit.

Setup

Four steps to a themed app

The only prerequisite is a shadcn-initialized project. Everything else is the CLI reading the public registry.

Register the @nebari namespace

Add the registry to components.json next to your existing style, tailwind and alias config. The {name} placeholder is what the CLI substitutes per item.

{
  "$schema": "https://ui.shadcn.com/schema.json",
  "registries": {
    "@nebari": "https://nebari-dev.github.io/nebari-design/r/{name}.json"
  }
}

Install the theme, then components

The theme is a registry:theme item. Installing it writes the token blocks into your global stylesheet. Components pull it in transitively, but install it explicitly once so the tokens are complete.

# tokens: one :root, one .dark, one @theme inline
npx shadcn add @nebari/theme
# any component; registryDependencies come along
npx shadcn add @nebari/button @nebari/dialog
# shared light/dark/system state + ThemeProvider
npx shadcn add @nebari/use-theme-preference

Load the fonts

The tokens name Geist and IBM Plex Mono but the registry does not ship webfonts. Without this step the app falls back to the system stacks, which is fine for a prototype and wrong for a product.

npm i @fontsource-variable/geist @fontsource/ibm-plex-mono
// app entry
import '@fontsource-variable/geist';
import '@fontsource/ibm-plex-mono/400.css';
import '@fontsource/ibm-plex-mono/500.css';

Mount the theme hook once and prevent the flash

Wrap the app in ThemeProvider so one hook instance owns the .dark class on <html>. Paste the output of themeBootstrapScript() at the top of <head> so a dark-preference user never sees a light frame while the bundle loads. This page runs the same trick with its own storage key.

import { ThemeProvider } from '@/hooks/theme-provider';

<ThemeProvider>
  <App />
</ThemeProvider>

The token contract

One semantic palette, both themes

Components consume role-based tokens, never primitives. This page is painted with the same values, so the theme picker in the header re-themes every block below. Switch it and watch the hex values change.

Surface stack

Four layers in stacking order. In light mode a card is separated from the canvas by its border, not its fill. In dark mode recessed surfaces lift instead of digging.

--canvas
--header
--card / --popover
--muted
input fill, zebra row, slider track

--background is deprecated. Its light value equals the header layer, which made headers invisible on pages painted with it. It stays for existing consumers. New page shells use bg-canvas.

Muted text on a muted surface uses text-muted-foreground-strong, not text-muted-foreground. The regular muted foreground fails contrast on the recessed fill.

Keep your overrides out of the Nebari block

A theme install overwrites every value it owns in the first matching :root, .dark and @theme inline block. That is how token updates reach apps. Put app-owned tokens in a second block after it; the cascade lets the later declaration win and the CLI never touches it.

/* App overrides: keep below the Nebari theme blocks. */
:root {
  --header-action-hover: #d9d9dc;
  --notification-badge: #d00000;
}
.dark {
  --header-action-hover: #4a4a50;
  --notification-badge: #e00000;
}
@theme inline {
  --color-header-action-hover: var(--header-action-hover);
  --color-notification-badge: var(--notification-badge);
}

Composition

Extend at the call site, never in ui/

Every component has the same shape: semantic token classes, stable data-slot and data-variant attributes, an exported cva function, and Base UI's render prop where the element is polymorphic. Once you have read one, you can use any.

Do

Pass classes; cn() lets yours win

<Button variant="outline" size="sm"
        className="w-full">
  Cancel
</Button>
Do

Swap the element with render

Nebari's equivalent of Radix's asChild. Classes, data-* attributes and props are merged onto the element you pass.

<Button render={<a href="/docs" />}>Docs</Button>
<Badge variant="outline"
       render={<a href="/tag/new" />}>new</Badge>
Don't

Edit components/ui/button.tsx

The next shadcn add regenerates the file and your change is gone. It also forks your app away from every other consumer of the same component, which is the thing a design system exists to prevent.

Don't

Restyle with raw hex or dark: variants

Tokens flip with the .dark class on their own. A hard-coded color or a dark: override is a second theme system that drifts from the first.

// no
<Card className="bg-[#f6e9ff] dark:bg-[#442655]" />
// yes
<Card className="bg-muted" />

Need a component the catalog lacks? Fall back to the upstream shadcn component and style it with the same semantic tokens. Check the manifest first with curl -s https://nebari-dev.github.io/nebari-design/r/registry.json, and inspect any item before installing with npx shadcn view @nebari/<name>.

The installed source is the API reference. Exact variant and size names live in each component's cva block and props type. That file, not any doc, is authoritative.

The theme picker is a menu radio group

Light, Dark and System live inside the profile menu as Base UI Menu.RadioItems, which render role="menuitemradio" with aria-checked. It only looks like a segmented control. Tabs would promise a tab panel that does not exist and fight the menu's arrow-key navigation. Set closeOnClick={false} so people can try modes without the menu snapping shut. Open the account menu above to see it work.

There is no avatar in the registry

Each app owns a small Avatar built on Base UI's primitive, kept outside components/ui/ so a later install cannot overwrite it. Base UI owns the image loading state, so the fallback renders whenever the image is missing or fails. Only render the notifications bell if the app has notifications.

Motion

Tokens for time, not magic numbers

The theme ships four durations, two easings and five ready-made animate-* utilities. Replay each demo below; they run on the real token values.

fade-in
animate-fade-in

--duration-base 200ms, --ease-standard

slide-up-fade
animate-slide-up-fade

--duration-base 200ms, --ease-emphasized

animate-skeleton-pulseReplay

--duration-loading 1600ms, infinite

active:scale-95Replay

--duration-fast 100ms, transform only

Hard rules

  • Gate on motion-safe: for every animation class. Nebari targets WCAG 2.1 SC 2.3.3. This page honors reduced motion the same way.
  • Reference tokens with parentheses in Tailwind v4: motion-safe:duration-(--duration-base). The v3 bracket form silently resets the duration to zero.
  • Animate opacity and transform only. Height, width, padding and top force reflows.
  • CSS and Base UI first. Base UI popups expose data-starting-style and data-ending-style for enter and exit transitions in plain CSS.

The cn() merge gotcha

tailwind-merge deduplicates your transition classes against the ones already in the component's cva block. A bare transition overwrites the component's transition-property and its color transition disappears. Re-enumerate every property you need.

<Button className={cn(
  'motion-safe:transition-[color,background-color,transform]',
  'motion-safe:duration-(--duration-base)',
  'motion-safe:active:scale-95',
)} />

For sequences CSS cannot express, use the Motion library through the render prop: <Button render={<motion.button … />}>. It is not a default dependency; install it only when needed.

Design source

The Figma variables library is the source of the color system. The primitive ramps and semantic tokens in globals.css are mirrored from it one to one, with the source hex recorded in comments. A test derives the theme item from that file and fails if they drift.
