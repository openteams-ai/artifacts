Part one

What WebGPU actually is

A W3C JavaScript API that gives web pages low-level access to the system GPU.

Not a graphics library like Three.js. A thin, portable layer the browser translates down to native APIs.

It does two things: rendering and general-purpose compute. WebGL only ever did the first.

The entry point is navigator.gpu.

WebGPU

The API you call. One portable surface over three native backends, with validation between your code and the driver.

Emphasize the second bullet. People assume WebGPU competes with Three.js. It sits underneath it.

Part one

Eight years, and one hard constraint

8

years from the first spec work to shipping by default in every major browser

Who built it

The W3C "GPU for the Web" Working Group. Apple, Google, Mozilla, Intel and Microsoft all at the same table.

Why it took so long

Any random website can run code on your GPU. So everything is validated, bounds-checked, and free of undefined behavior.

What that constraint bought

One API that behaves the same across Metal, Direct3D 12 and Vulkan. Safety shaped the entire design. It is why the API is explicit.

The safety point is the interesting one for a design audience. It explains why the API feels verbose. Every bit of ceremony buys a guarantee that a webpage cannot crash or read another process's GPU memory.

Part one

What it replaces

WebGL

  • OpenGL ES, a 2007-era mobile API, mapped onto the web
  • One global, mutable state machine
  • State re-validated on every single draw call
  • Rendering only
  • GLSL shaders
  • CPU-bound long before the GPU is

WebGPU

  • Designed for modern GPU hardware from scratch
  • Explicit objects you create once and reuse
  • Validated once, when the pipeline is created
  • Rendering and compute
  • WGSL shaders
  • Work recorded on the CPU, submitted in batches
Do not let this turn into WebGL-bashing. WebGL still works everywhere and is still the right fallback. The point is that its design assumptions are eighteen years old.

Part one

It brings its own shader language

@group(0) @binding(0)
var<storage, read_write> data: array<f32>;

@compute @workgroup_size(64)
fn main(
  @builtin(global_invocation_id) id: vec3<u32>
) {
  data[id.x] = data[id.x] * 2.0;
}

WGSL

Rust-flavored syntax, designed alongside the API rather than borrowed from an older one.

Compiled at runtime

The browser translates it to SPIR-V, Metal Shading Language or HLSL depending on the platform.

It is not GLSL

If anyone here has written shaders before, this is new syntax for them too.

Do not teach WGSL. Show it for ten seconds so the room knows it exists and that it looks approachable. The example doubles every number in an array. That is a compute shader, not a rendering one.

Part two · How it works

Three steps, seven objects

Every WebGPU program, rendering or compute, follows the same three steps. Click one.

Connect to a GPU

Adapter → Device

Ask the browser for a physical GPU, then open a connection to it. This is where you learn what the hardware can do, and where you find out there is no usable GPU at all.

Describe the work, once

Buffers and textures · Shader modules · Pipelines · Bind groups

Allocate GPU memory, compile your WGSL, and bundle shaders and settings into a pipeline that is validated when it is created. Bind groups say which data each shader reads. This is the expensive part, and you do it up front.

Record, then submit

Command encoder → Queue

Each frame, record a list of commands on the CPU and hand the whole batch to the GPU in one call. A draw fills pixels; a dispatch runs your shader as thousands of parallel copies. Nothing blocks while the GPU works.

Rendering and compute share all of this. Only the last step differs: a render pass draws to a canvas, and a compute pass dispatches work and writes the results to a buffer.

Stay at this altitude. Say the three steps, click through them, and move on; nobody needs the API names memorized. The point to land: step two is the heavy one, and you do it once. That sets up the next slide.

Part two · How it works

The mental model underneath all of it

WebGL · A conversation.

CPUGPU

0 driver calls this frame

Set state, draw. Set state, draw. Hundreds of driver calls every frame, and the CPU becomes the bottleneck long before the GPU does.

WebGPU · Declare, then batch.

CPUGPU

0 submit this frame

Describe the work up front, pay a heavy setup cost once, and the frame loop gets cheap. You are building command lists, not having a dialogue.

The win is mostly reduced CPU overhead, not raw GPU speed.

This is the takeaway you actually want people to leave with. Play the frame, then say it slowly and let it sit for a beat.

Part two · How it works

Everything is asynchronous

if (!navigator.gpu) return fallback();

const adapter = await navigator.gpu
  .requestAdapter();
if (!adapter) return fallback();

const device = await adapter.requestDevice();

device.lost.then(info => {
  if (info.reason !== "destroyed") reinit();
});

Two gates, not one

navigator.gpu only means the API exists. The non-null adapter means you can actually render.

Errors arrive later

Through device.lost and pushErrorScope, not thrown exceptions.

It looks different

Initialization is structurally unlike WebGL. This is what people trip over first.

This slide sets up the hardware slide that follows. The null adapter is the hinge between the two.

Part three

What this means for different hardware

Integrated graphics count

Intel Iris and UHD, AMD integrated, Apple Silicon's unified GPU. All real GPUs, all run WebGPU fine. "No GPU" usually just means no discrete card.

Discrete GPUs

More memory and headroom. powerPreference: "high-performance" hints toward one, but it costs battery, so only ask when you need it.

No GPU at all

Servers, containers, headless CI, some VMs. requestAdapter() resolves to null. There is no graphics card to describe.

Software fallback

Chrome's Dawn can run on SwiftShader, a CPU-based Vulkan. It needs the system Vulkan loader and Mesa drivers, or it still returns null. And it is 10 to 100× slower. Fine for tests, useless for a demo.

This machine

Asking the adapter…

Even on supported hardware, capability varies. Read adapter.limits and adapter.features. Browsers also blocklist old GPUs and bad drivers.

The practical rule for the room: always await requestAdapter(), check for null, and keep a WebGL2 or canvas2d path behind it. The "This machine" panel is why you demo on your own laptop rather than a borrowed one. Adapter limits differ per machine, and you can show that live.

Part four

And where it does not belong

Most UI does not need this.

CSS, canvas2d and SVG are still correct

For the overwhelming majority of what we build, they are simpler, more accessible and better supported.

The setup cost is real

Pipelines, buffers, bind groups and a new shader language before a single triangle appears on screen.

Reach for a library first

Three.js, Babylon.js and PlayCanvas already support it. For most cases the renderer swap is close to a one-line change.

Being honest here buys you credibility for everything else you said. WebGPU earns its complexity at scale, or when you need compute. Not before.

Part four

WebGPU outside the browser

WebGPU is a spec, and the spec has native implementations. That makes it a portable GPU layer for projects that never touch a web page.

Rust · graphics

wgpu

The WebGPU implementation inside Firefox, also shipped as a standalone library. One API over Vulkan, Metal, Direct3D 12 and OpenGL natively, or WebGPU and WebGL2 when compiled to WebAssembly.

Rust · deep learning

Burn

A deep learning framework with a WGPU device. The same model trains and runs on any GPU wgpu can reach, with no CUDA requirement.

Rust · ML inference

Ratchet

Hugging Face's cross-platform inference framework, built on wgpu. One codebase runs models in the browser and natively.

The pattern: WebGPU is becoming a portable GPU target, much as WebAssembly became a portable CPU target. Write the compute once and run it on whatever GPU the user has.

Keep this to a minute. The point for this room: the concepts from part two transfer beyond the browser. wgpu is the same code Firefox ships, so the adapter, device, pipeline and queue you just learned are the same objects in a native Rust app or an ML framework.

Part five

Demos

Each runs the same work on this machine's GPU and on its CPU, so the difference is measured here, not claimed. Without WebGPU only the CPU side runs, which is the slide-12 fallback in practice.

01 · Data at scale

idle

A compute shader moves every particle each frame, and a render pipeline draws them from the same buffer, so the data never leaves the GPU. The CPU version does the same math in JavaScript and paints pixels into a 2D canvas. Move the pointer over the canvas to pull the swarm.

02 · Heavy work per element

idle

The same Mandelbrot image, 230,400 pixels, each looping up to the iteration limit. Every pixel is independent and expensive, which is the shape of work GPUs are built for, and the shape of ML inference.

Run local copies, and have a recording ready. Drivers and conference wifi both fail at the worst possible moment. Present from your own laptop, not a borrowed one. Adapter limits differ per machine.

Open the deck before you start so the adapter is already requested. Demo one: start on WebGPU at 250,000, then flip to CPU and let the room watch the frame rate collapse. Flip back and go to a million; WebGPU holds. That is the data visualization card from slide 13, live. Demo two: race at 5,000 iterations, then at 20,000. The gap widens as the work per pixel grows. That is why the GPU wins at ML, and it is the honest version of the claim: for light work per element, the CPU is fine. The GPU time includes reading the image back; the first race also compiles the shader, which is reported separately.

Part five

A chat model, running on this GPU

WebLLM compiles small language models to WebGPU. The weights download once and the browser caches them. After that, every token is generated on this machine, and nothing you type leaves it.

03 · Local chat

not loaded

Pick a model and load it. The first load downloads the weights from Hugging Face; later loads come from the browser cache.

What is happening

The same pieces as part two: an adapter, a device, compute pipelines for the transformer layers, and buffers holding the weights. Each generated token is a batch of dispatches.

Why it matters

No server, no per-token bill, no user data in transit. This is the local ML inference card from slide 13, working.

What it costs

Hundreds of megabytes of download and GPU memory, for a model far smaller than a hosted one. Fine for classification, extraction and short drafts. Not a replacement for a frontier model.

Load the model before the talk so it comes from the cache; on conference wifi a 280 MB download will not finish in time. Ask the room for a prompt. Point at the tokens-per-second figure: that is this laptop's GPU doing the work. Then say the privacy line out loud: nothing typed here leaves the machine.
